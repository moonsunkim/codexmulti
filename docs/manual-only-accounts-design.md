# 계정별 자동 선택 제외 설계

작성일: 2026-09-18

상태: 승인된 설계 구현과 로컬 검증 완료. 0.2.14 릴리스에 포함.

검토 기준: CodexMulti 0.2.13, `8ee0089`.

## 1. 요구사항

사용자가 확인한 요구사항은 다음과 같다.

> 자동 선택에서는 빼되, 내가 직접 선택하면 프록시에서 사용 가능

계정을 등록한 채로 특정 계정의 사용량을 아껴 두고, 필요한 때 직접 선택해 사용할 수 있어야 한다. 보관 이유는 추정이며, 구현이 특정 용도에 종속될 필요는 없다.

자동 선택 참여 여부, 현재 선택된 계정, 계정의 사용 가능 상태를 별도로 관리한다. 자동 선택에서 제외해도 로그인 정보와 사용량 조회는 유지한다. 사용량 자동 새로고침 설정과 주기는 이 기능으로 변경하지 않는다.

## 2. 변경 전 동작

0.2.13 계정 메뉴에는 이미 ‘자동 전환 대상에서 제외’라는 문구가 있었다. 그러나 실제 동작은 프록시 계정을 `PAUSED`로 만드는 것이었다.

- `core/src/shell_model.zig`: 계정 메뉴의 제외 동작을 프록시 pause로 전달한다.
- `core/src/ui_projection.zig`: `READY` 계정에만 수동 전환을 노출한다.
- `proxy/src/failover.mjs`: `selectReady()`가 paused 계정을 건너뛴다. `switchTo()`도 같은 선택 함수를 사용하므로 제외한 계정으로 수동 전환할 수 없다.
- `proxy/src/server.mjs`: 명시적 credential reload/refresh 경로는 `reloadReady()`를 호출한다. 이 함수는 pause와 cooldown을 함께 해제하므로, 사용자의 제외 의사와 인증 상태 복구가 섞여 있다. 주기적 토큰 갱신 전체가 이 동작을 한다는 뜻은 아니다.

기존 pause는 재시작 후에도 저장된다. 문제는 저장 유무가 아니라, 자동 선택 제외와 모든 사용 중지가 같은 상태라는 점이다.

## 3. 사용 규칙

계정마다 **‘자동 전환에 포함’** 설정을 둔다. 끄면 **‘수동 전용’** 계정이다. 아래 표는 인증과 한도가 정상일 때의 동작이다.

| 동작 | 자동 전환 포함 | 수동 전용 |
| --- | --- | --- |
| 자동으로 첫 계정 선택 | 가능 | 제외 |
| 다른 계정의 한도 도달 후 자동 선택 | 가능 | 제외 |
| 사용자가 ‘이 계정으로 전환’ 선택 | 가능 | 가능 |
| 직접 선택한 뒤 다음 요청 처리 | 가능 | 가능 |
| 한도 초기화 후 자동 후보 복귀 | 가능 | 제외 유지 |
| 로그인·사용량 조회 | 기존 규칙 유지 | 기존 규칙 유지 |

직접 선택한다고 ‘자동 전환에 포함’ 설정이 켜지지는 않는다. 한도 초과, 인증 오류, 일시 중지 등 기존의 사용 제한도 우회하지 않는다. 사용할 수 없는 계정을 직접 선택하면 이유를 보여 주고 현재 선택을 유지한다.

### 수동 선택의 범위와 유지 기간

승인된 수동 선택의 범위와 유지 규칙은 다음과 같다.

- 수동 선택은 현재 프록시를 공유하는 모든 클라이언트에 적용한다. 대화별 고정 기능은 이번 범위에 포함하지 않는다.
- 선택 이후 시작하는 요청부터 적용한다. 이미 처리 중인 응답은 끝까지 유지한다.
- 다른 계정을 선택하거나 ‘자동 선택으로 돌아가기’를 누르거나, 선택 계정이 한도·인증 문제 등으로 사용 불가해질 때까지 유지한다.
- 앱 또는 프록시 재시작만으로 사용자의 수동 선택을 해제하지 않는다. 재시작 시 계정이 존재하고 사용 가능할 때만 복원한다.
- 수동 계정이 사용 불가해지면 수동 선택을 해제하고 자동 참여 계정에서 다음 대상을 찾는다. 해당 계정의 한도가 나중에 초기화되어도 수동 선택은 복원하지 않는다.
- 현재 요청을 재시도할 수 있는지는 기존 failover 조건을 따른다. 이미 응답을 시작했거나 재전송할 수 없는 실패를 이 기능 때문에 재시도하지 않는다.

예: A·C가 자동 참여, B가 수동 전용이라면 A의 한도 도달 시 C로 넘어간다. 사용자가 B를 직접 선택하면 B로 처리한다. 이후 B의 한도에 도달하면 사용 가능한 A·C로 넘어가고, B가 회복되어도 자동으로 돌아가지 않는다.

### 사용 중에 설정을 바꾸는 경우

- 자동으로 선택된 A를 수동 전용으로 바꾸면, 이미 시작한 요청은 완료하고 다음 요청부터 다른 자동 참여 계정을 선택한다.
- 사용자가 직접 선택해 사용 중인 A를 수동 전용으로 바꾸면, 명시적인 수동 선택은 유지한다. UI에는 ‘수동 전용 · 사용 중’으로 표시한다.
- 수동 전용을 다시 자동 참여로 바꿔도 현재 계정을 강제로 바꾸지 않는다. 다음 자동 선택의 후보로만 복귀한다.
- 자동 참여 계정이 하나도 없어도 설정을 허용한다. 사용할 수 있는 수동 선택이 있으면 해당 계정으로 처리하고, 없으면 ‘자동 전환할 계정이 없습니다. 계정을 직접 선택하거나 자동 전환에 포함해 주세요’라고 안내한다. 제외 계정을 임의로 사용하지 않는다.

## 4. 화면 설계

계정의 더보기 메뉴에 다음 두 동작을 둔다.

```text
이 계정으로 전환…
✓ 자동 전환에 포함
```

체크를 끄면 계정 행에 ‘수동 전용’을 표시한다. 인증 오류나 한도 대기 상태는 별도로 표시한다. ‘수동 전용’ 자체를 장애·비활성 상태처럼 회색 처리하지 않는다.

상세 설명은 ‘자동으로 선택되지 않습니다. 직접 선택하면 사용할 수 있습니다.’로 한다. 수동 사용 중에는 ‘자동 선택으로 돌아가기’ 동작을 제공한다.

상단 통계는 다음 의미로 맞춘다.

- ‘자동 전환 가능 N개’: 자동 참여 설정이 켜져 있고 현재 선택 가능한 계정 수.
- ‘풀 잔여량’: 자동 참여 계정에 기존 잔여량 계산 규칙을 적용한다. 수동 전용 계정은 분자와 분모에서 모두 제외한다.
- 전체 등록 계정 수가 필요하면 별도로 표시한다. 자동 참여 계정이 없을 때 풀 잔여량은 `—`로 표시해 한도 소진에 따른 0%와 구분한다.
- ‘처리 중 N개’: 기존 실제 요청 집계를 그대로 유지한다. 수동 전용 계정에서 처리하는 요청도 포함한다.

UI 문구는 Zig core의 다국어 카탈로그에서 관리하고 Swift에는 표시 데이터만 전달한다.

## 5. 데이터와 선택 로직

### 서로 다른 세 가지 상태

| 데이터 | 역할 | 저장 위치 |
| --- | --- | --- |
| `auto_select_enabled` | 사용자가 정한 자동 참여 여부, 기본값 true | 앱 account registry → 프록시 config |
| `selection_source`, `manual_account`, `selection_revision` | 현재 선택 출처, 대상, 선택 세대 | 프록시 state, auth-file 식별자로 재연결 |
| paused / invalid / cooldown | 기존 계정 사용 제한 | 기존 프록시 state |

앱 registry를 자동 참여 설정의 원본으로 삼는다. 프록시 config는 이를 전달하고 runtime은 적용한 값을 보고한다. 기존 `enabled`는 사용량 조회와 계정 import에도 영향을 주므로 재사용하지 않는다. 수동 전용 계정도 프록시 config와 인증 registry에 남겨 둔다.

설정과 선택은 앱의 안정적인 account ID에 연결한다. 목록 순번이나 표시 이름을 식별자로 쓰지 않는다. 기존 auth-file 매핑은 이전 상태를 연결할 때 활용한다. 이름 변경·정렬·재로그인으로 설정이 초기화되지 않도록 한다.

선택 순서는 다음과 같다.

1. 명시적으로 선택한 계정이 있고, 현재 사용 가능하며 해당 요청에서 이미 실패한 대상이 아니면 사용한다.
2. 그렇지 않으면 자동 참여 계정 중 기존 우선순위와 가용성 규칙으로 선택한다.
3. 자동 후보가 없으면 기존 대기·실패 규칙을 따른다. 쿨다운 계정 탐색과 제한 해제 확인용 요청도 자동 참여 계정에만 한정한다.

이 규칙을 일반 HTTP, Responses WebSocket의 각 `response.create`, failover 재선택, `earliestCooldown()` 모두에 적용한다. 상태 조회와 UI도 동일한 판정 결과를 사용한다.

불투명하게 중계하는 기존 WebSocket 연결은 이미 연결한 계정을 중간에 바꿀 수 없다. 해당 경로는 새 연결부터 적용하며, Responses WebSocket은 기존 연결에서도 다음 응답 요청부터 적용한다. 기존 연결을 끊어 적용하지 않는다.

### 실행 중 적용과 동시성

자동 참여 설정 변경은 별도의 좁은 제어 API로 적용한다. 전체 config 재로딩이나 프록시 재시작에 의존하지 않는다.

설정 저장 후 실행 중인 프록시에 전달하고 적용 결과를 확인한다. 프록시가 적용했다고 응답한 뒤 접수하는 요청은 새 정책을 따라야 한다. 후보 선택 후 실제 요청 접수 사이에도 정책을 다시 확인해, 변경 직전에 골라 둔 계정을 뒤늦게 사용하지 않도록 한다.

수동 선택에는 선택 세대 번호를 둔다. 과거 계정의 늦은 실패가 새 수동 선택을 지우지 않도록, 실패한 요청이 참조한 수동 선택과 현재 선택이 같은 경우에만 해제한다.

프록시가 꺼져 있으면 설정을 저장해 다음 시작 시 요청을 받기 전에 반영한다. 실행 중인 프록시에 적용하지 못했다면 ‘적용 대기’ 또는 오류를 표시한다. 적용 확인 전에 제외가 완료된 것처럼 표시하지 않는다. 오래된 runtime이 기능을 지원하지 않으면 업데이트 필요를 표시한다.

이 동기화는 설정 변경·프록시 시작·재연결 시 수행한다. 이 기능을 위해 숨은 주기적 사용량 새로고침을 추가하지 않는다.

## 6. 기존 상태 이전

- 기존 일반 계정과 새 계정은 자동 참여를 기본값으로 한다.
- 기존 제외 계정은 자동 참여 false로 이전한다. 기존 pause는 임의로 해제하지 않는다. ‘수동 전용 · 일시 중지’로 구분하고 명시적 중지 해제를 제공한다.
- 중지 해제와 자동 참여 재설정은 별도 동작이다. 중지 해제가 자동 참여, cooldown 해제, 인증 복구까지 함께 수행하지 않게 한다.
- 기존 cursor에는 선택 출처가 없으므로, 이를 근거로 수동 전용 계정의 사용을 승인했다고 추정하지 않는다. 새 방식으로 직접 선택한 기록부터 수동 선택을 복원한다.
- 명시적 reload/refresh, 주기적 토큰 갱신, 재로그인은 자동 참여 설정을 바꾸지 않는다. 삭제 후 새로 추가하는 계정은 새 계정 기본값을 따른다.

## 7. 구현 범위와 검증 기준

변경 지점은 `account_registry.zig`, proxy import/config, `failover.mjs`, `server.mjs`, Responses WebSocket, core 제어 클라이언트·shell·projection·문구, Swift 계정 메뉴와 bridge 계약이다. bridge fixture는 생성기로 갱신한다.

회귀 테스트는 다음 사용 시나리오를 다룬다.

1. A·C 자동, B 수동 전용: 최초 선택·한도 failover·쿨다운 탐색 어디에서도 B를 자동 선택하지 않는다.
2. B를 직접 선택하면 HTTP와 기존 Responses WebSocket의 다음 요청에 B를 사용한다. B의 자동 참여 값은 false로 유지된다.
3. B가 사용 불가해지면 가능한 자동 참여 계정으로 전환하며, B가 회복돼도 자동 복귀하지 않는다. 재시도 불가 요청은 중복 전송하지 않는다.
4. 자동 참여 계정이 0개일 때 명시적 수동 선택 유무에 따라 처리·안내가 정확히 갈린다.
5. 토큰 갱신·재로그인·이름 변경·정렬·앱/프록시 재시작 후 자동 참여 설정이 유지된다. 유효한 명시적 수동 선택도 복원된다.
6. 이미 처리 중인 응답을 끊지 않으며, 설정 적용 응답 이후 새로 접수한 요청은 변경된 정책을 따른다. 과거 요청의 실패가 새 수동 선택을 해제하지 않는다.
7. 적용 실패·구버전 runtime·프록시 종료 상태를 실제 적용 완료와 구분한다. 재연결과 시작 시 저장된 정책을 먼저 반영한다.
8. 수동 전용 계정이 자동 풀 수치에 포함되지 않고 실제 처리 중 요청 수에는 정상 반영된다. 사용량 자동 새로고침 설정은 그대로 유지된다.

첫 구현은 계정별 참여 토글, 명시적 수동 선택, 자동 선택 복귀까지로 한정한다. 계정별 시간표, 기간 제한, 우선순위 편집, 대화별 고정은 별도 요구가 생기면 검토한다.

## 8. 구현 확인

- 프록시: `npm test`로 HTTP와 Responses WebSocket의 자동 제외, 수동 사용, 한도 failover, 재시작 복원, 기존 설정 이전을 확인한다.
- 동시성: `request admission rechecks a stale candidate` 테스트는 자동 제외·수동 선택 적용 직전에 고른 후보가 새 요청에 사용되지 않는지 확인한다. `excluding an account preserves its started response`는 시작한 응답이 완료되고 후속 요청만 다른 계정으로 가는지 확인한다.
- core: `zig build test test-bridge export-fixtures`로 저장 실패 복원, 오프라인 설정 보존, 재연결 적용, 풀 계산, 표시 문구와 bridge 계약을 확인한다.
